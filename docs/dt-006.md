# DT-006 – Vertrauensgrenzen für beaufsichtigte Exec-Agenten

## Entscheidung

**NO-GO für einen echten Agentenlauf.** DT-006 liefert eine Offline-Prüfung der
Hostgrenzen und zusätzliche unabhängige Inhaltskontrollen im bestehenden
Simulationspfad. Es enthält keinen Live-Runner und keine Betreiberfreigabe.
Ein positives Einzelresultat, gespeichertes JSON, eine Umgebungsvariable und ein
Agenten-PASS können `CodexExecGateway.require_simulation()` nicht öffnen.

Basis des Audits ist der gemergte DT-005-Commit
`737dffc705b368e550e0a38803068e23b9c56d09`. Die Ausführung hier erfolgt in einer
verwalteten Codex-Arbeitsumgebung, **nicht im vorgesehenen GitHub Codespace**.
Der vom Auftraggeber berichtete `CODEX_EXEC_OK`-Texttest mit CLI 0.163.0 und
bestehendem ChatGPT-Login ist ein Schnittstellenhinweis, kein Isolationsbeleg.
Es gab im Rahmen dieses Auftrags keine Modellaufrufe, Login-/Secret-Änderungen,
Installationen zusätzlicher Sicherheitskomponenten, Buchungen, Deployments oder Merges.

## Zielarchitektur und Codespaces-Machbarkeit

Ein Codespace bildet einen Entwicklungsplatz ab. Eine Grenze gegenüber anderen
Codespaces sagt nichts über Controller, Modellprozess und Projektbefehle innerhalb
desselben Codespaces aus. Für den konkreten Ziel-Codespace liegen hier weder
Kernel-/Mount-/UID-Messungen noch ein genehmigter Credential-Broker vor.
Deshalb ist kein entscheidender Live-Punkt als nachgewiesenes GO markiert.

| Grenze | Erforderliches Design | Im Ziel-Codespace nachgewiesen? |
| --- | --- | --- |
| Controller | Getrennte Host-/VM-Identität; Journal, Git-Objekte, Prüfinstruktionen und Auditablage nur dort schreibbar. Agenten sehen weder Controllerpfad noch FD, Host-Home, SSH-, GitHub- oder Docker-Socket. | **UNVERIFIZIERT / NO-GO**. Keine Messung dort; ein gemeinsamer Devcontainer oder eine gemeinsame UID erfüllt dies nicht. |
| Rollen | Je Rolle eigener User-/Mount-/PID-/IPC-/Netzraum, Capability-Drop, eigener privater Schreibbereich; keine Signal-, `/proc`-, Lese- oder Schreibrechte auf andere Rollen. Für stärkere Mandantentrennung getrennte UID-/VM-Grenzen. | **TEILWEISE HOSTABHÄNGIG / NO-GO**. Namespaces lassen sich hier ohne neue Privilegien nutzen; das beweist keine getrennten Host-UIDs und keine Verfügbarkeit im Codespace. |
| Prüfsnapshots | Controller exportiert aus verifiziertem Git-Commit einen SHA-/SHA-256-gebundenen Dateibaum ohne beschreibbares `.git`; QA und Security bekommen denselben Inhalt über getrennte, extern lesend gemountete Snapshots. Eigene Ergebnis-/Tempbereiche. | **UNVERIFIZIERT / NO-GO**. Neue Inhaltskontrollen erkennen bleibende Manipulation; sie ersetzen keinen unveränderlichen Mount. |
| Credential-Broker | Vorhandener Login ausschließlich im vertrauenswürdigen Modell-/Brokerprozess. Tools erhalten weder Authdatei, Refreshmaterial, Umgebungsvariable, offenen FD noch erreichbaren privilegierten Socket. Prozessidentität außerhalb der Rolle durchsetzen. | **NICHT IMPLEMENTIERT / NO-GO**. Für CLI 0.163.0 ist hier kein unterstützter, separat überprüfter Modell-/Tool-Executor-Vertrag belegt. Login-Verfügbarkeit ist keine Brokerfähigkeit. |
| Modell-Egress | Extern erzwungene Trennung: nur Modellprozess zum minimal notwendigen Modell-/Authdienst; Projekttools ohne DNS/HTTP/TCP/UDP/Unix-/Abstract-Socket-Pfad zum Broker oder Internet. Broker bindet Run, Rolle und Kontingent vor Weiterleitung. | **NICHT IMPLEMENTIERT / NO-GO**. Lokale Netz-Negativtests mit abgeschaltetem Rollen-Netz beweisen keinen funktionsfähigen Modell-Egress. |
| Ressourcen/Abbruch | Unabhängiger Supervisor mit absoluter Lease; pro Run begrenzte cgroup/VM für Summe von CPU, Speicher und PIDs; gesamte Einheit bei Timeout, Controllerverlust oder SIGKILL beenden und quarantänisieren. | **NICHT NACHGEWIESEN / NO-GO**. RLIMIT, `killpg` und `--die-with-parent` genügen insbesondere bei abgesetzten Nachfahren nicht. |
| Belegkollektor | Außerhalb aller Rollen: Git-/Contentprüfung, ausgeführte Abnahmen, Snapshotidentität, Auditquellen und Kontingente gemeinsam an Run/Repo/Config/HEAD binden. | **NUR SIMULATION**. Neue Diagnosequellen sind keine Live-Attestierungen. |

Das Vorhandensein von `bwrap`, Docker, `sudo`, Worktrees oder `--sandbox read-only`
ist kein zusammengesetzter Nachweis dieser Grenzen. DT-006 verändert weder
Sysctls noch Capability-Sets des Hosts, cgroup-Delegationen, Containerrechte,
Firewallregeln oder Zugangskonfigurationen. Insbesondere wird Docker-Zugang nicht
benutzt, um fehlende Hostrechte zu ersetzen.

Der Broker ist ein zentraler Machbarkeitsblocker: Eine Authdatei im für Tools
lesbaren Home ist ungeeignet. Ebenso reicht ein HTTPS-Proxy nicht, wenn Tools
denselben privilegierten Proxyanschluss erreichen können. Vor einer Implementierung
muss ein unterstützter CLI-/Tool-Split nachgewiesen werden, bei dem die Grenze
außerhalb von Prompt, Projektcode und Codex-Kindprozess liegt. Ist das mit dem
bestehenden ChatGPT-Login nicht belegbar, bleibt der vorgesehene Host NO-GO.

## Offline-Probes und Aussagegrenzen

```sh
python -m developer_team.boundary_probe > /tmp/dt006-boundary-report.json
# Exitcode 2 ist die erwartete NO-GO-Entscheidung, auch bei positiven Einzelprobes.
python -m unittest tests.test_boundaries tests.test_exec -v
```

Die Probe verwendet ausschließlich selbst erzeugte temporäre Dateien, künstliche
Credentials, eigene lokale Listener und einen eigenen Python-Schlafprozess mit
einem künstlichen Umgebungscredential. Sie liest keine echten Tokendateien,
startet weder `codex` noch Projektbefehle und kontaktiert keinen externen Host.
Die Dateiziele und Listener werden vom Controller positiv geprüft, bevor ein
verweigerter Zugriff als PASS zählen darf; Listener bleiben auch danach geprüft.

Vor jedem Rollenprogramm werden getrennte User-, Mount-, PID-, Netz-, IPC- und
UTS-Namespaces geprüft. Anschließend läuft derselbe feste controllerseitige
Angriffscode separat für Orchestrator, Developer, QA und Security:

| Probe | Konkreter negativer Versuch |
| --- | --- |
| Credential / Controller | Künstliche Authdatei lesen und künstliches Controllerjournal überschreiben; außerhalb des Mounts. |
| Cross-Role | Alle jeweils drei fremden Rollen-Ausgabedateien lesen und überschreiben. |
| Snapshot | Unabhängige vorhandene Dateien schreiben, löschen, umbenennen und chmod ausführen; synthetische `.git/config` überschreiben. |
| Prozess / Supervisor | Nur den eigenen künstlichen Hostprozess über `/proc/PID/environ` lesen und harmlose `SIGCONT`-Signale an ihn bzw. den Controller senden. Getrennte PID-Namespaces müssen diese Zugriffe verhindern. Kein Signal an fremde Prozesse. |
| DNS / HTTP / TCP | UDP-Anfrage an eigenen DNS-Transport-Canary sowie HTTP-/TCP-Verbindung zu nachweislich erreichbaren Host-Loopback-Listenern versuchen. Keine externe DNS-Auflösung. |
| Sockets | Eigenen Dateisystem-Unix-Socket und zufällig benannten Abstract-Unix-Socket erreichen. |
| Schreibbereich | Positivkontrolle im privaten Rollen-`/tmp`; danach prüft der Controller Inhalt, Modus und Dateimenge sämtlicher Host-Canaries. |

Nur erwartete Verweigerungs-Errnos zählen als bestandene negative Probe. Ein
Timeout oder unbekannter Fehler ergibt `UNSUPPORTED`. Fehlendes Bubblewrap,
verweigerte Namespaces oder unvollständige Ergebnisse ergeben `UNSUPPORTED`
ohne Host-Python-Fallback. Die Gesamtaussage ist immer **NO-GO**. Insbesondere
bleiben Broker, Modell-Egress, separate Hostidentitäten, Ressourcen und externer
Supervisor als `UNSUPPORTED` enthalten. Dieser Collector kann keine Freigabe laden.

Diese lokale Netprobe belegt die getesteten Loopback-/Socket-Verweigerungen in
einem Netznamespace ohne Modellzugang. Sie prüft weder eine Internet-Allowlist
noch DNS-Rebinding, IPv6-/Proxy-Exfiltration bei geöffnetem Modellpfad oder einen
Credential-Broker. Die Rollenprobes laufen nacheinander mit kontrollierten
Cross-Role-Zielen, nicht als vollständiger konkurrierender Vier-Rollen-Dauerlauf.
Der synthetische Prozess ersetzt keine getrennte Host-Identität. Ein harter
Supervisor-Kill mit cgroup-/VM-weitem Cleanup ist ohne externen Supervisor nicht
prüfbar und wird ausdrücklich nicht als bestanden dargestellt.

## Untrusted-result- und Auditgrenze

`SnapshotSeal` vergleicht tatsächliche Dateien mit den Git-Blobidentitäten und
bindet zusätzlich HEAD, Tree, Pfad, Git-Modus und SHA-256 des Inhalts. Damit kann
`git update-index --assume-unchanged` einen abweichenden Prüfinhalt nicht verbergen.
Ein zweites Inventar umfasst auch ignorierte Dateien, Dateimodi und Git-Metadaten.
Symlinks, Hardlinks und Spezialdateien werden verworfen; das Inventar ist auf
4096 Dateien und 64 MiB begrenzt. Das Baselineobjekt bleibt im Controllerprozess.

Exec vergleicht Controller und Rollenkopie vor dem Aufruf und überprüft beide
Inventare vor und nach dem vorhandenen Patchvalidator. Vor einem erneuten Git-Aufruf
werden Änderungen an den Metadaten erkannt. Der bestehende Validator prüft
Dateigrenzen, geschützte Dateien, Rolle und Ergebnisbindung weiterhin unabhängig
vom gelieferten PASS. Der bestehende Engine führt seine Abnahmen selbst aus und
stellt deren Receipts getrennt von den simulierten Reviewer-Aussagen aus.

Erst nach erfolgreicher Ergebnisprüfung ergänzt der Controller den abgeschlossenen
Transport um `controller_verification` und ein Ereignis `exec:controller-verified`.
Gespeichert werden Herkunft `controller:exec-result-validator-v1`, HEAD, Tree,
Inhalts-/Inventarhashes, Hash der unabhängig ausgeführten Check-Ergebnisse im
Rollenkontext sowie Payload-/Patchhashes. `execution_attested` bleibt **false**;
Origin bleibt **simulated**. Bei erkannter Snapshotmanipulation entsteht kein
solcher Eintrag für den betroffenen Aufruf. Der Diagnoseeintrag bezieht sich auf
Snapshot-, Envelope- und Patchprüfung. Rollenpayload-Schema und PASS-Konsistenz
prüft `StructuredAgents` anschließend; auch danach kann die Stufe noch scheitern.
Ein zuvor `completed` genannter Transport ist deshalb noch keine erfolgreiche
Inhaltsprüfung, kein Reviewbeleg und keine Freigabe.

Diese Diagnoseeinträge sind gespeicherte Auditdaten. Sie erzeugen keine neuen
`EvidenceAuthority`-Receipts. Agentenoutput, eine nachträglich geänderte SQLite-Datei
oder eine gespeicherte GO-Aussage können damit weder Testergebnisse ersetzen noch
beim Neustart unabhängige Evidenz herstellen. Für spätere Live-Attestierungen
fehlt weiterhin ein außerhalb der Rollen geschützter Kollektor/Auditspeicher.

Der Fingerabdruck erkennt **bleibende** Manipulation. Ein gleichberechtigter
Hostprozess kann Dateien während der Prüfung verändern und anschließend
wiederherstellen oder den Controller selbst angreifen. Hashes, Inventare und
getrennte Kopien schließen diesen TOCTOU-/Same-UID-Angriff nicht aus. Das ist ein
Grund für die unveränderte Live-Sperre, keine zugesicherte OS-Unveränderlichkeit.

## Erst nach separater ausdrücklicher Betriebsfreigabe

Ein späterer, eigenständig geprüfter Produktionsrunner muss technisch auf eine
einzige beaufsichtigte Runde begrenzt werden. Folgendes ist ein Entscheidungsentwurf,
**kein jetzt akzeptiertes Freigabeformat und keine implementierte Aktivierung**:

- Bindung an eindeutige Run-ID, `oxfrd1337/developer-team`, Controller-/Basis-SHA,
  effektiven Config-/Anforderungshash, exakte Dateigrenzen, Host-/Image-/Brokerrevision,
  Modellspezifikation, Operator und absolute Ablaufzeit.
- Genau eine Runde `orchestrator`, `developer`, `qa`, `security`, je höchstens ein
  Rollenstart, maximal vier Starts insgesamt; keine Reparatur-/Retryrunde.
- Vorschlag: höchstens 300 Sekunden Gesamtlaufzeit, 60 Sekunden pro Rolle und
  zusätzlich höchstens 16 brokerseitig gezählte Modellrequests insgesamt, maximal
  vier pro Rolle. Vier CLI-Starts begrenzen allein nicht interne Modellrequests.
  Sämtliche Grenzen vor Freigabe verbindlich festlegen und vor Dispatch abbuchen.
- Extern erzwungene Ressourcen-/Ausgabelimits und unabhängiger Supervisor mit Lease;
  Stopverantwortlicher, Abbruchsignal, Quarantäne und Reconciliation vorab benennen.
- Kein Merge, Deployment, Kauf, fremdes Repository oder Schutzregelwechsel. Bei
  fehlender, veralteter, widersprüchlicher Evidenz oder unklarem Ausgang sofort
  stoppen; keine automatische Wiederholung und keine Rückerstattung des Intents.

Aufruf-/Zeit-/Ausgabelimits sind keine garantierten Euro- oder Token-Caps. Auch ein
Abbruch kann bereits angefallene Providerkosten nicht zurücknehmen. Auth-, Host-,
Budget- und Pilotfreigabe müssen deshalb nach den fehlenden Nachweisen separat
und ausdrücklich erfolgen. Der jetzige Code akzeptiert keines dieser Dokumente
als Startberechtigung.

Tatsächlich ausgeführte Prüfungen und offene Akzeptanzpunkte stehen in
[dt-006-validation.md](dt-006-validation.md); der gespeicherte Hostbericht ist
ausdrücklich ein Beobachtungsartefakt und keine Attestierung.
